# Chunk P0001-C05 — `status` reports plugins

**Goal:** `tack status` and `status --json` show each selected plugin's
state in each harness it targets, read from the agents through their own
CLIs, so a user can see whether `sync` delivered what the manifest asks.
P0001-C04 made `sync` deploy plugins; D3 comes next because `doctor` (D4)
and the TUI's Plugins tab (D7) both read these states. Unit a is the C04
review's follow-up: the README's and the agent skill's manifest examples
get a test (#35).

## Kickoff notes

Unit b is the heart: read design.md §9 *Plugin states* sentence by sentence
(rewritten at this cut), with DEC-15 (the state order) and DEC-16 (a failing
list is `unavailable`). Every state reads what `sync` reads, so b is a
second implementation of `sync`'s step 2 and step 3 conditions: the

### P0001-C05-b — Each selected plugin's state

**Build** (design.md §9 *Plugin states*; DEC-15, DEC-16):

- `status.PluginStatus`: `name`, `source`, `harnesses` (harness → state,
  for the harnesses the plugin targets), `version`, `path`. `Status.plugins`,
  one per selected plugin (one per source for a collided name), sorted by
  name and then source. `SourceStatus.plugins`: the names the source
  selects in `plugins.plan`, `[]` for a source that selects none.
- A `PluginState` literal of the seven states, and one function that gives
  the first that applies in DEC-15's order.
- What a harness has from tack's marketplace (name → enabled; Claude Code's
  at user scope) is read by one function that `sync._Plugins._harness` (its
  first `installed` set and the DEC-14 refresh) and `status` both call.
  `sync`'s behavior doesn't change.
- For each harness that takes plugins and that a selected plugin targets,
  `agents.inventory` runs once. Its failure, a missing CLI or a failed
  command, makes every plugin there `unavailable` (DEC-16); a `tack`
  marketplace that isn't tack's (`agents.is_tack`) makes them `conflict`.
- `collision`: the name is in `plugins.plan`'s collisions, in every harness
  the plugin targets. `stale` as *Plugin states* says: tack's copy missing or
  its hash not the directory's, in any harness; in Codex also the record's
  hash missing or not the directory's. A plugin whose `directory` is None,
  or whose directory `tree_hash` can't read, is never `stale`.
- `version`: `catalog.version` with the plugin's directory's files, or the
  entry alone when it has no directory. `path`: tack's copy
  (`<marketplace>/plugins/<name>`) when it is a directory, else None.
- `status` runs no command but the two `list` ones, writes nothing, creates
  no directory, and exits `0`.

**Tests**, in `tests/test_status.py` against the stand-ins:

- Each state from a fixture: `installed` after a real sync; `missing`
  before one; `stale` from tack's copy (a plugin file edited after a sync:
  both harnesses) and from Codex's hash alone (the record's Codex hash
  changed: `installed` in Claude Code, `stale` in Codex); `disabled`
  (`standins.plugin(..., enabled=False)`); `conflict` (a foreign `tack` in
  one harness, the other unaffected); `collision`; `unavailable` from a
  removed CLI and from a failing `plugin list`.
- DEC-15's order where states overlap: disabled and stale is `disabled`; a
  collided name in a harness whose CLI is removed is `collision`.
- Agreement with `sync`: for each fixture above, a `sync.sync(cfg,
  dry_run=True)` lists a `copy` of a plugin, or a `reinstall` of it in a
  harness, exactly where `status` calls it `stale` among the plugins it
  calls `stale` or `installed`, and an `install` exactly where it calls one
  `missing`; after a real sync, those are `installed`.
- A selected plugin tack can't deploy (an `npm` entry): `missing` in both
  harnesses, `version` from its entry, `path` null.
- Through `cli.main(["status", "--json"])`: each plugin object's keys are
  exactly `name`, `source`, `harnesses`, `version`, `path`, and each source
  has `plugins`. A manifest without plugins gives `"plugins": []` and makes
  no agent call.
- Read-only: with plugins selected and tack's data directory removed,
  `status` leaves `tree(home)` unchanged and every call is a `list`; a
  plugin limited to `codex` makes no `claude` call.

**Done when:** those pass, and every existing `status`, `cli` and `sync`
test passes unchanged.

### Findings

1. design.md §9 *Plugin states* said `stale` is "exactly what `sync` would
   copy or reinstall", and the brief's kickoff repeated it; but `sync` first
   holds a source (DEC-12) or checks out its pin, so for a source whose
   state isn't `ok` `status` can say `stale` or `missing` where `sync` then
   changes nothing (#38, from the report's *Doc inconsistencies found*).
   The code is right and the doc was wrong, my error at the cut: `status`
   reads a source as it is, as it does for a held source's skills. Note;
   fixed in this review commit (DEC-17; *Plugin states*; a line in the
   README and the skill) and recorded as `brief-checklist §5`, whose sweep
   found the same promise in the *`doctor` checks* text being written for
   C06. Closes #38.
2. `tack status` and the TUI's Sources detail call a `path` source whose
   root is gone "its skills directory isn't there" (`text.SOURCE_STATES`),
   wrong for a `skills = []` source since P0001-C04 made it need no skills
   directory; `doctor` tells the cases apart. Follow-up; filed as #40 and
   scheduled as P0001-C06-a.
3. The TUI's worker calls `status.status` and `doctor.run` together, so with
   plugins selected it now runs the agents' `list` commands, and from D4 runs
   each twice per refresh. Note; the brief left it to D7, and the project's
   D7 now says its worker reads each agent once.
4. The stand-in keys Claude Code installs by id, so one plugin can't be
   installed at two scopes (#39, from the report). Note; left as an idea.
5. `README.md`'s first paragraph ran past 80 columns after unit c's edit.
   Note; rewrapped in this review commit.
