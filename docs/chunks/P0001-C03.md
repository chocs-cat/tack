# Chunk P0001-C03 — `sync` runs the plugin steps

**Goal:** `sync` deploys the plugins `plugins.plan` selects: it brings
tack's marketplace up to date and runs §9 *Deploying*'s five steps in each
harness through the agents' CLIs, recording what it installed in
`state.json`. Plugin names collide across harnesses (DEC-11). The manifest
still rejects `plugins`, so only tests reach the new pass, with `Config`s
built as P0001-C02's tests build them; for everyone else `sync` behaves
exactly as before and runs no agent CLI. The next chunk holds a held
source's plugins (DEC-12), accepts `plugins` and `skills = []`, and
documents it, which completes D1 and D2.

## Units

### P0001-C03-a — Plugin names collide across harnesses

**Build:** in `plugins.plan` (§9 *Selecting plugins*; DEC-11): a name two
or more sources select collides whatever harnesses each targets. Its
collision maps it to every harness any of them targets, in
`config.PLUGIN_HARNESSES` order, and to the sources, and it is in no
harness's plugins. A plugin counts whether or not it is deployable, as
before.

**Tests:** in `tests/test_plugin_plan.py`, rewrite
`test_plugins_for_different_harnesses_do_not_collide` (now a collision in
both harnesses, in neither map) and `test_collisions_only_where_harnesses_
overlap` (a `"*"` source and a `codex` source collide in both). One source
selecting `x` for `claude-code` and another selecting a different name for
`codex` still don't collide.

**Done when:** those pass; restoring the per-harness rule fails them.

### P0001-C03-b — The record's plugins, and keeping a plugin's copy

**Build:**

- `deploy.Record` gains `plugins`: harness → plugin name → a frozen record
  of `source` and `hash` (§9 *Plugin ownership*; DEC-6). `load_record`
  accepts a record without the key (no plugins) and rejects a malformed one
  (not that shape, or a non-string `source` or `hash`) with the existing
  "not a version 1 ownership record" error. `save_record` writes the key
  only when some harness lists a plugin, leaving out harnesses that list
  none, harnesses and names sorted; `version` stays `1`.
- `plugins.update` takes `keep`, plugin names whose copy and entry in
  tack's catalog stay as they are: their copies are neither refreshed nor
  deleted, and their entries are carried over from the catalog on disk (a
  kept name with no copy, or no entry there, has neither). A name both
  wanted and kept is kept.
- `plugins.Update` gives each wanted plugin's hash: its directory's, which
  its copy has once copied (a dry run included). `sync` records it.

**Tests:** in `tests/test_deploy.py`: a
record with plugins round-trips; a record without `plugins` loads with none,
and a record with links only is written byte for byte as before; each
malformed shape is rejected; a harness with no plugins left is dropped on
save. In `tests/test_marketplace.py`: a kept plugin's stale copy isn't
refreshed and its catalog entry survives an update that doesn't want it; a
kept name with no copy gets no entry; `Update`'s hashes equal
`tree_hash` of each plugin's directory.

**Done when:** those pass, and every existing record and marketplace test
passes unchanged.

### P0001-C03-c — `sync` runs the plugin steps

**Build:** in `src/tack/sync.py`, after the skills (§9 *Deploying*,
*Plugin ownership*; DEC-1, DEC-3, DEC-5, DEC-6, DEC-11):

- **Whether to run.** A harness that takes plugins is *involved* when a
  selected plugin targets it (any plugin in a plan source's `selected`,
  deployable or not), the record lists a plugin there, or tack's
  marketplace directory exists. With no harness involved, the plugin pass
  does nothing: no CLI, no `plugins.update`, no record change.
- **Problems from the plan.** Each collision is a `collision` problem
  naming the sources and harnesses (worded like the skills one). Each
  selected plugin that can't be deployed, and each broken catalog, is a
  `source` problem (its reason, or `CatalogError`'s message) with the
  source and, as its path, the catalog file. A selected plugin from another
  repository is a `source` problem too: tack doesn't deploy those yet (D8).
  Missing names and ignored entries aren't `sync` problems.
- **tack's marketplace.** The *wanted* plugins are the harness maps'
  `InSource` plugins, one per name (DEC-11). The *kept* names are the
  collided ones and those from another repository. When anything is wanted
  or kept, `plugins.update(paths, wanted, keep=kept)` runs; its copies are
  `copy` changes (with the plugin's source), its catalog write a `write`,
  and each failure a `source` problem whose plugin is then kept too. From
  here on, *wanted* means wanted and not kept: no step installs,
  reinstalls or uninstalls a kept plugin (DEC-12's first case).
- **Each harness**, in `config.PLUGIN_HARNESSES` order, when involved:
  - `agents.inventory`. A missing CLI is an `agent` problem when a selected
    plugin targets the harness, and is passed over otherwise; any other
    failure is an `agent` problem. Either way the harness's steps stop and
    its record entries stay.
  - A foreign `tack` (`agents.is_tack` false) stops the harness's steps; it
    is a `conflict` problem when a selected plugin targets the harness or
    the record lists one there.
  - Its *installed* plugins are those its list shows from the marketplace
    named `tack` (Claude Code's at `user` scope), enabled or not (DEC-5).
  - Step 1: register when a selected plugin targets the harness and tack's
    marketplace isn't registered there. If registering fails, the
    harness's install steps stop.
  - Step 2: install each wanted plugin targeting the harness that isn't
    installed, and record its source and hash. A wanted plugin that is
    installed but not recorded is recorded with no command in Claude Code,
    and in Codex is reinstalled (step 3), since its copy's age is unknown.
  - Step 3, Codex only: reinstall (`agents.install` again, change action
    `reinstall`) each installed wanted plugin whose recorded hash differs
    from its hash now, and record the new hash.
  - Step 4: uninstall each installed or recorded plugin that is neither
    wanted for the harness nor kept, and forget it. In Claude Code, a
    recorded plugin its list doesn't show isn't installed: forget it with
    no command. In Codex, uninstall every recorded one, since its list
    hides some.
  - Step 5: unregister when no selected plugin targets the harness and
    tack's marketplace is registered there.
  - Each command's failure is an `agent` problem with the agent's message
    (`Outcome.error`), the harness, and the plugin's source where there is
    one; the other plugins carry on, and a failed install or uninstall
    leaves the record as it was.
- **Copies and the directory.** A copy that is neither wanted nor kept is
  deleted (`plugins.drop`, a `delete` change) once no record lists it and
  no uninstall of it failed. With nothing selected anywhere, tack's
  marketplace directory is deleted (`plugins.remove`, a `delete` change)
  once every harness whose CLI is on `PATH` has it unregistered and the
  record lists no plugin.
- **The result.** `Action` gains `copy`, `register`, `install`,
  `reinstall`, `uninstall` and `unregister`, and `ProblemKind` gains
  `agent`. The five agent changes carry the harness and, as their detail,
  the command line (`str(Command)`). `text.VERBS` gives the five agent
  actions `run`/`ran` and `copy` `copy`/`copied`, so the text output reads
  `codex  would run codex plugin add x@tack --json`.
- **Dry run.** Only the `list` commands run; every other step is a change
  listed as if it had succeeded; nothing is written (the marketplace, the
  record, no CLI state).
- **The record** is saved when its links or its plugins changed, never in
  a dry run.

**Tests:** in a new `tests/test_sync_plugins.py`, against the stand-ins,
with `path` sources and catalogs under the temporary directory and
`plugins` set as P0001-C02's tests set it:

- A first sync: per harness, the exact commands in order (register, then
  install), the copies, tack's catalog keeping upstream fields, and the
  record (source, hash, `version` 1). A second sync runs only `list`
  commands and changes nothing.
- A changed file in a plugin: the copy refreshes, Codex reinstalls, and
  Claude Code gets no command beyond `list`. A recorded hash that differs
  in Codex reinstalls; an installed, unrecorded plugin is recorded
  (Claude Code) or reinstalled (Codex).
- Deselecting one plugin: uninstall in each harness, the record forgets
  it, the copy is deleted. Deselecting the last: uninstall before
  unregister in both, then the directory is deleted. A plugin limited to
  `codex` leaves Claude Code unregistered.
- A Codex plugin the record lists but `codex plugin list` hides is
  uninstalled when deselected; a Claude Code one its list doesn't show is
  forgotten with no command.
- A disabled plugin is neither installed again nor enabled; no `enable` or
  `disable` command appears in any test's call log.
- A foreign `tack` in one harness: a `conflict`, no command in that harness
  beyond `list` (with `adopt` too), the other harness deploys, and the
  problem makes `cli.main(["sync"])` exit `1`. A plugin installed from
  another marketplace, and that marketplace, are never touched.
- A missing CLI in a harness a plugin targets: an `agent` problem, the
  skills still link, the other harness deploys. In a harness no plugin
  targets, with no record and no marketplace directory: no problem, no
  call.
- A failed install: an `agent` problem with the agent's message, the other
  plugins install, and the record lacks it. A failed `list`: that harness
  stops.
- Collisions: neither plugin deploys in any harness, and an earlier copy,
  catalog entry and installs of that name are left as they were.
- An undeployable plugin, a broken catalog, and a plugin from another
  repository: a `source` problem each, and the source's other plugins
  deploy. A dangling symlink in a plugin fails only that plugin, which
  keeps its earlier copy and install; a symlinked file elsewhere is copied
  as its target.
- A dry run: only `list` commands in the call log, the home tree byte for
  byte unchanged (with a marketplace and record already there), and
  changes listing each command line.
- A manifest with sources but no plugins, and no marketplace directory:
  the call log stays empty and `state.json` is as before
  (`review-checklist §1`).
- The text output of a plugin sync (`text.result_text`) for one change of
  each new action.

**Done when:** those pass, `sync` with no plugins selected and no
marketplace directory is unchanged (every existing test passes unchanged),
and `config.parse` still rejects `plugins`.

### What landed

**a.** `plugins.plan` groups the selected plugins by name across every
source. A name two or more sources select collides whatever harnesses each
targets: its collision maps it to every harness any of them targets (in
`config.PLUGIN_HARNESSES` order) and to the sources, and it is in no
harness's plugins (§9 *Selecting plugins*; DEC-11).

**b.** `deploy.Install(source, hash)` and `Record.plugins` (harness → name →
`Install`; §9 *Plugin ownership*; DEC-6). `load_record` accepts a record
without `plugins` and rejects any other shape, or a non-string `source` or
`hash`, with the existing "not a version 1 ownership record" error; unknown
keys inside an entry are ignored, as unknown top-level keys already were.
`save_record` writes `plugins` only when a harness lists one, harnesses and
names sorted, so a links-only record is written byte for byte as before.
`plugins.update(…, keep=…)` leaves kept names' copies alone and carries
their entries over from tack's catalog on disk (none without a copy or an
entry); a name both wanted and kept is kept. `Update.hashes` gives each
wanted plugin's directory hash except a failed one's, in a dry run too.

**c.** `sync.sync` runs `_Plugins` after the skills (in `sync.py`, beside
`_Linker`). It follows the brief's bullets. Every agent command goes through
`agents.py`, and every step is a `Change` whose detail is `str(Command)`.
Failures are `agent` problems worded `<step> failed: <agent's message>`
(`installing a failed: …`, `listing its plugins failed: …`). A missing CLI
reads "`` `codex` isn't on PATH, so codex gets no plugins ``". Plan
problems (collisions, undeployable plugins, broken catalogs, plugins from
another repository) are reported whether or not a harness is involved, since
they only come from reading the manifest's selections. `Action` gains the
six plugin actions and `ProblemKind` gains `agent`. `text.VERBS` reads
`would run` / `ran` and `copy` / `copied`. P0001-C02's `configure` helper
(and `market` with it) moved to `tests/helpers.py`.

Three choices where the brief left the shape open:

- **Claude Code's recorded hash.** It stays the one recorded at install, or
  when tack first recorded an install it found. That is the literal reading
  of *Plugin ownership* ("tack's copy when tack installed it there"). Claude
  Code loads the copy in place, so nothing reads that hash.
- **A recorded plugin's source follows the manifest.** If another source
  now supplies the same name, the record names the new source in both
  harnesses. Codex reinstalls only if the hash differs. *Plugin ownership*
  says each record entry carries "the source it came from", and DEC-12 will
  rely on that.
- **The directory goes in one `delete`.** When tack's marketplace directory
  is deleted, that is the only change listed, not one `delete` per copy too.
