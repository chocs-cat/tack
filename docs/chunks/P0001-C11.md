# Chunk P0001-C11 — plugins from other repositories, deployed

**Goal:** a catalog entry naming another git repository and a commit
deploys like a plugin in the source: `sync` clones the repository into the
plugin's clone, brings it to the catalog's commit, copies the plugin (the
whole repository, or a `git-subdir`'s `path`) into tack's marketplace and
installs it; `status`, `doctor`, the TUI and `add` treat it as `sync` does.
This is the wiring P0001-C10 built the clones for, and it finishes D8 but
for the repository and commit in `status --json` and the TUI, and `outdated
--diff` between commits. Unit a fixes #54 first, since this chunk makes it
reachable for every plugin from another repository.

## Kickoff notes

Unit b is the one to read slowly. Its rule is in design.md *Plugins from
other repositories*, pinned at this cut: a plugin's files are its clone's
only while the clone is `ok`, so `sync` brings the clones first and only
then reads them; anything that reads the plan as it is (a dry run, `status`,
`doctor`, the TUI) sees a clone that isn't `ok` as a plugin with no
directory, kept. Today's code already treats "no directory" as "kept" (that
is how an other-repository plugin is kept now), so most of the wiring is the
plan giving an `ok` clone's directory, and `plugins.undeployable` no longer
refusing these plugins. **No test may reach the network:** today's tests name
`github.com/acme/…` entries, which `sync` and `add` would now clone. Every
entry a test syncs or adds is a `file://` remote; a `github` entry stays only
where nothing clones (the plan, `outdated`, a dry run). The reviewer will
grep for it. Unit c then holds `doctor`, the TUI and `add` to what `sync`
reports (DEC-19), with the parity tests that already exist.

## Units

### P0001-C11-a — a clone tack can't bring to its commit is deleted (#54)

**Build** (design.md *The lockfile*, last paragraph; DEC-22; fixes #54):

- `sources._bring` deletes a directory it cloned in this run when the fetch
  or the checkout that follows fails, then raises as it does now, so the
  path is `not cloned` again. A directory that was there before the run is
  never deleted. Both `sync_git` and `sync_clone` get it, through `_bring`.

**Tests:** in `tests/test_sources.py`, a git source with no checkout and a
pin its remote lacks: `sync_git` fails with today's message and leaves no
checkout; `sync_git` with a good pin then clones and checks it out (it
refused it for local changes before). In `tests/test_clones.py`, the same
for a clone; and a clone already there, `off its commit` with a commit the
remote lacks: it fails and is left as it was (`tree()` unchanged, state
`off its commit`).

**Done when:** those pass, and every existing `sources`, `clones`, `sync`,
`update` and `add` test passes unchanged.

### P0001-C11-b — `sync` and `status` deploy them

**Build** (design.md *Plugins from other repositories*, *Deploying*, *Plugin
states*; DEC-12, DEC-17, DEC-21):

- The plan gives a plugin from another repository its clone (`Clone.of`
  with its source's and its own name), and as its directory the clone's
  `directory` only when the clone is `ok` as the plan is made; otherwise
  none, so `plugins.kept` keeps it, as today. Its `kept` and the
  `Selected.directory` comments say so (no more "until D8").
- `plugins.undeployable` gives no reason for such a plugin: `sync`'s
  problems, `doctor`, `add` and the TUI stop saying "tack doesn't deploy
  those yet".
- `sync` brings the clone of each plugin it would copy (selected, a name no
  other source selects, from a source it doesn't keep) to its commit with
  `sources.sync_clone`, after the sources and before tack's marketplace, in
  name order. Each step is a change `clone` or `checkout` with the plugin's
  source and the clone's path; a failure is a `source` problem `plugin
  '<name>': <the SourceError>`, with the plugin's source and the clone's
  path. Then the plugins are read as the plan now gives them: a plugin whose
  clone is `ok` is copied, installed and reinstalled as one in the source
  is; one whose clone isn't is kept (DEC-12). A dry run lists the steps,
  brings nothing, and keeps a plugin whose clone isn't `ok`.
- `status` needs no code of its own beyond the plan: its states and
  `version` read an `ok` clone's directory, and a clone that isn't `ok`
  gives no directory (never `stale`; `version` from the entry).

**Tests** (`tests/test_sync_plugins.py` with the stand-ins, and
`tests/test_status.py`; every remote a `file://` URL with two commits, the
entry naming the older one):

- A `url` entry: `sync` gives `clone`, `checkout`, `copy`, then the installs
  in both agents; tack's copy holds the older commit's files and no `.git`.
  A `git-subdir` entry: the copy holds only its `path`.
- `tack update` of a git source whose catalog moves the entry's `sha` to
  the newer commit: the next `sync` gives `checkout`, `copy` and Codex's
  `reinstall`, and no Claude Code command (D8's Done-when; walk both runs'
  reads, brief-checklist §4).
- A clone with local changes: `sync` reports the problem with the clone's
  path, exits `1`, and the plugin's copy, tack's catalog, its installs and
  the record are as they were. A clone deleted after a sync: the next
  `sync` gives `clone` and `checkout`, and no `copy` or install (the files
  hash the same).
- A dry run from nothing: `clone` and `checkout` for the plugin, no `copy`
  or install for it, nothing written (`tree(home)`), only `list` commands
  run. A collided name and a held source's plugin: no clone made.
- `remove` after such a sync: the plugin uninstalled in both agents, then
  its clone a `delete`.
- `status`: not cloned → `missing`, `version` the entry's; after `sync` →
  `installed`, `version` from the clone's `plugin.json`; the entry moved to a
  commit the clone isn't at, with different files → `installed`, not
  `stale`.
- brief-checklist §7, the tests this unit changes:
  `test_plugins_tack_cannot_deploy` drops its `r` (a `github` entry `sync`
  would now clone; its other problems stay);
  `test_add_plugins_installs_them`'s refusal row for `r` and
  `test_add_plugin_refusals_come_in_order`'s `r` message go (`add` accepts
  it now; c tests that); `test_a_source_with_no_skills_lists_its_plugins`
  now lists `r` and then adds it, so its `ELSEWHERE` becomes a `file://`
  entry and the refusal reads `'b', 'good', 'r'`; `test_doctor_plugins.py`'s `_elsewhere` fixture in
  `PROBLEMS` goes (a dry run reports nothing about a plugin not yet cloned),
  as does `test_source_findings_and_collisions`'s `r` row (its `found[6:]`
  index follows); `test_tui.py`'s
  `test_a_plugins_detail_gives_the_problem_sync_reports` drops its `r`
  case (c adds a clone's). Say in the report what each became.

**Done when:** those pass; every other existing test passes unchanged; no
test clones from a host (`grep -rn "github.com" tests/` shows only entries
nothing syncs or adds).

### P0001-C11-c — `doctor`, the TUI and `add` say what `sync` does

**Build** (design.md *`doctor` checks*, *The Plugins tab*, *Adding and
removing sources*, *Plugins from other repositories*, all pinned at this
cut; DEC-19):

- One function gives the problem `sync` reports about a plugin's clone
  (`in the way`, `local changes`), as `sync` words it: `sync`, `doctor` and
  `plugins.problems` all call it, for a plugin whose clone `sync` would
  bring. `sources.sync_clone(clone, dry_run=True)` raising is one way.
- `doctor`: a `not-synced` finding for it under *A source*, located at the
  clone; such a plugin gets no state finding (reported once, for its
  source). A plugin whose clone is `not cloned` or `off its commit` gets
  state findings as any other (`missing`, `disabled`; never `stale`) and no
  source finding.
- The TUI's plugin detail gives it (`plugins.problems`).
- `add` checks a plugin from another repository by its entry alone (no
  clone's files read, even one already there).
- README (*Plugins*: the "this release deploys plugins whose files are
  inside the source" paragraph, and `add`'s refusals) and
  `skills/tack/SKILL.md` (the same paragraph) say plugins from other
  repositories are cloned at the catalog's commit and deployed, and what a
  clone with local changes does.

**Tests:**

- `test_doctor_plugins.py`'s `PROBLEMS` gains "clone in the way" and "clone
  with local changes" (each a `file://` entry, its clone made by
  `sync_clone` first), so `test_problems_agree_with_sync` holds `doctor` to
  the dry run (brief-checklist §6). A clone not cloned: `missing` in each
  harness, no source finding. A plugin recorded in Codex, now selected for
  Claude Code only, its clone not cloned: no leftover finding.
- `test_tui.py`'s `test_a_plugins_detail_gives_the_problem_sync_reports`
  gains a clone with local changes, compared with the dry run's problem.
- `test_edit.py`: `add --plugin r` for a `file://` entry writes the table,
  and its `sync` clones and installs `r`; with a clone of `r` already
  there with local changes, `add` still accepts it, and its `sync` reports
  the clone's problem (exit `1`, the table written).

**Done when:** those pass, and every other existing `doctor`, TUI and `add`
test passes unchanged; README and the skill say what `sync` does with these
plugins.

### What landed

**a — a clone tack can't bring to its commit is deleted (#54).**
`sources._bring` wraps the fetch and the checkout that follows a clone: on a
`SourceError`, a directory this call cloned (`not there`) is deleted with
`shutil.rmtree` and the error re-raised, so the path is `not cloned` again.
A directory that was there before is never touched. `sync_git` and
`sync_clone` both get it through `_bring` (DEC-22).

**b — `sync` and `status` deploy them.** `plugins.Selected` gains `clone`
(`Clone.of(paths, source, plugin, where)` for an `InRepository` plugin), and
its `directory` is the clone's `directory` only when the clone is `ok` as the
plan is made (`plugins._files`, replacing `_directory`; the state is read
once per selected plugin, not per harness). `plugins.undeployable` no longer
refuses these plugins. `sync._Plugins._clones` runs after the plan's
problems and before tack's marketplace: for each plugin it would copy, in
name order, it brings the clone, records `clone`/`checkout` with the
plugin's source and the clone's path, and reports a failure as a `source`
problem `plugin '<name>': <error>` at the clone. When a real run took any
step, it makes the plan again (the brief's first suggested shape), so no
clone's files are read before `sync` brings it; a dry run lists the steps
and keeps a plugin whose clone isn't `ok` through `plugins.kept` as before.
`status` has no code of its own. Comments that said "until D8" now say what
the code does.

**c — `doctor`, the TUI and `add`.** `plugins.brought(plan, held=())` names
the plugins whose clones `sync` brings; `plugins.bring(sel, dry_run=…)`
brings one and returns `(steps, error)`. `sync`, `doctor` (`_blocked`) and
`plugins.problems` all call them, so a clone `in the way` or with `local
changes` gives the error `sync` reports (from a dry run). `doctor`: a
`not-synced` source finding at the clone, `plugin 'r' from 'one' can't be
brought to its commit, so tack leaves it as it is: <sync's error>`; such a
plugin gets no state finding. The state findings now cover every deployable,
uncollided plugin that isn't unreadable or blocked (was: every one with a
directory), so a clone `not cloned` or `off its commit` reads `missing` or
`disabled` (never `stale`) located at the clone's plugin directory, and,
being kept, gives no leftover. The TUI detail gets the problem through
`plugins.problems`. `edit._unfit` reads no files of a plugin with a clone.
README (*Plugins*: the catalog paragraph, `add`'s refusals, `doctor`'s
`not-synced` bullet) and `skills/tack/SKILL.md` (the same paragraph, the
`doctor` bullet, and a *Files* row for the clones) say what `sync` does.

Deviations, where the brief left it open: the doctor finding's wording
(above) follows the "can't be copied, so tack leaves it as it is" shape of
the unreadable-files finding, with `sync`'s error after the colon; a state
finding for a clone's plugin is located at `clone.directory` whether or not
it is cloned (`sel.directory` is None until it is `ok`).
